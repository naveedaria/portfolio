Technical PM Teardown · Linq Developer Platform

Cutting Time-to-First-Agent & Hardening Webhook/Voice Observability

Before applying for the Technical Product Manager role, I audited Linq's public developer surface—quickstart, CLI, Node & Python SDKs, webhook delivery semantics, and Voice/SIP docs—through the lens of a developer trying to ship a reliable messaging/voice agent into production.

Scope & Sources Inspected: docs.linqapp.com (Quickstart, Auth, Webhooks, Messaging, Voice/SIP), linq-team/linq-cli (@linqapp/cli), linq-team/linq-node (v0.86.3), and linq-team/linq-python (v0.71.3). Everything below reflects directly observed behavior in the public docs and SDK source—no assumptions.

01 / Observed Developer Friction Log

5 concrete places developers lose momentum between signup and production

1. Three conflicting onboarding stories & three env var names Onboarding · Time-to-First-Run

The Quickstart doc says you need "A bearer token from your Linq representative." The Authentication page says to self-generate a token at dashboard.linqapp.com/api-tooling, yet lower on the same page tells developers to "Request new tokens periodically from your Linq representative." Meanwhile, linq-cli already supports instant self-serve linq signup via email OTP. Across those same surfaces, env vars drift three ways: LINQ_API_KEY (docs), LINQ_API_V3_API_KEY (Stainless SDK default), and LINQ_TOKEN (CLI).

Why it matters: Developers hit unnecessary friction in the first 5 minutes—and bounce if they think sandbox testing requires a sales call when self-serve CLI signup already exists.

2. Quickstart vs. SDK README drift (plus empty message: {}) SDK Ergonomics · Node & Python

docs.linqapp.com recommends starting with POST /v3/messages omitting from (auto line-pool selection). Both linq-node and linq-python READMEs instead show chats.create with a hardcoded from number and an empty message: {} object. Both SDKs also expose duplicate phoneNumbers/phone_numbers and phonenumbers namespaces, while linq-python omits webhooks.unwrap() from api.md (requiring an undocumented optional extra pip install linq-python[webhooks]) and lags behind linq-node on MCP server packaging.

Why it matters: Python is the primary language for AI agent developers. Hiding webhook verification behind an undocumented optional extra adds avoidable setup errors on first integration.

3. Webhook timeout + retry semantics create an AI-agent "double-text" trap Webhooks · Agent Reliability

Linq enforces a 10s webhook response timeout with exponential backoff over 30 minutes (at-least-once, out-of-order possible). Multi-step AI agents frequently take 15–45s to call tools/LLMs; naive synchronous handlers time out, trigger retries, and send duplicate texts. Outbound deduplication via message.idempotency_key exists in the JSON body (not an HTTP header), but is undocumented in both SDK READMEs. Worse, manual replay via a Linq rep (up to ~70 min) mints a new event_id—silently bypassing consumer dedupe tables keyed on event_id.

Why it matters: Messaging agents are uniquely unforgiving—one duplicate or dropped reply breaks end-user trust immediately.

4. No zero-downtime webhook secret rotation Webhooks · Production Security

signing_secret (whsec_...) is returned once on POST /v3/webhook-subscriptions and cannot be rotated in place—rotating requires deleting and recreating the subscription. Because target_url must be unique per account, teams cannot stand up a parallel subscription on the same URL before tearing down the old one.

Why it matters: Even though Standard Webhooks natively supports space-separated dual signatures during rotation, developers currently have to accept brief webhook downtime or spin up throwaway endpoints to rotate keys.

5. Voice / SIP operational blind spots Voice Channel · Debuggability

Voice is API-only today with three debugging gaps: (a) neither GET /v3/phone_numbers nor GET /v3/sip-profiles/{id} returns which numbers are bound to which SIP profile (only assigned_number_count), forcing external state tracking; (b) PUT .../sip-profile takes ~5 minutes to propagate with no readiness status or event; (c) call_voice.* events and call records omit SIP failure codes/reasons and cover inbound calls only (Outbound Early Access has no webhooks or call history, and linq-cli has no Voice/SIP commands).

Why it matters: Developers wiring voice agents cannot self-diagnose failed SIP handshakes or verify whether a new profile assignment is live without escalating to support.

02 / Roadmap Prioritization Call

What to build first vs. what can wait

With a small product/eng team scaling both messaging and voice, the highest leverage is compressing Time-to-First-Successful-Run (TTFSR) and eliminating support-gated debugging before adding surface area.

P0 · Now

Unify Quickstart, Env Vars & Python/Node Webhook Ergonomics

Lead docs with linq signup + linq webhooks listen -f; accept LINQ_API_KEY as a first-class fallback in CLI and Stainless SDKs; fix SDK README examples to match POST /v3/messages; document webhooks.unwrap() and message.idempotency_key prominently in both Node and Python (bundle standardwebhooks by default in linq-python). Metric moved: TTFSR (<10 min) and sandbox→production conversion.

P0 · Now

Self-Serve Webhook Delivery Inspector, Replay & Dual-Key Rotation

Ship GET /v3/webhook-subscriptions/{id}/deliveries, self-serve replay that preserves original_event_id, and a 24h dual-signing-secret rotation endpoint (see mini-spec below). Metric moved: Support tickets for missed webhooks and production reliability rate.

P1 · Next

Voice / SIP Observability & Outbound Event Parity

Return sip_profile_id + propagation_status on GET /v3/phone_numbers; add sip_status_code and failure_reason to call_voice.* events; extend call_voice.* webhooks & call records to Outbound Calling before exiting Early Access; add linq voice / sip-profiles commands to linq-cli.

Defer

Full Dashboard GUI for SIP Trunk Configuration

Why wait: Teams configuring SIP TLS trunks and SRTP codecs live in code, CLI, and Terraform. A read-only status view + CLI commands solves 90% of the pain at 20% of the engineering cost; wait until self-serve Voice volume justifies full CRUD UI.

Defer

Warm Call Transfer & Per-Call Dynamic SIP Headers

Why wait: Shipping advanced telephony features before outbound call logs and SIP failure diagnostics exist multiplies debugging load for both developers and Linq support. Lock in observability first.

03 / Mini-Spec (P0)

Agent-Safe Webhook Delivery Lifecycle, Replay & Secret Rotation

Goal: Let developers see every delivery attempt, inspect exact failure reasons, replay failed events without double-texting users, and rotate signing secrets with zero downtime—fully backward-compatible with existing ?version=2026-02-03 integrations.

1. Delivery State Machine

queued ──▶ delivering ──▶ delivered (2xx within 10s)
               │
               ├── (5xx / 429 / timeout / conn err, attempts < 10 & window < 30m)
               ▼
            retrying ──▶ delivering (exp backoff + jitter, cap 10m)
               │
               ├── (4xx != 429, DNS failure, HTTPS downgrade, or 30m exhausted)
               ▼
          dead_lettered ──(POST .../replay within 7d)──▶ replayed ──▶ delivering

2. API Additions (Additive, Non-Breaking)

  • Inspect live deliveries & failures: GET /v3/webhook-subscriptions/{subId}/deliveries?status=retrying,dead_lettered&event_id=... — returns delivery state, attempt count, HTTP status, latency (ms), response snippet (first 512 bytes), next retry timestamp, and exact failure class (timeout_10s, http_5xx, tls_error, dns_failed).
  • Self-serve idempotent replay: POST /v3/webhook-subscriptions/{subId}/deliveries/{deliveryId}/replay — assigns a new delivery_id (logged in header webhook-id per Standard Webhooks) while preserving the original event_id inside the JSON body and adding "is_replay": true. Existing integrations deduplicating on event_id remain safe unless they explicitly opt to reprocess replays.
  • Zero-downtime secret rotation: POST /v3/webhook-subscriptions/{subId}/rotate-secret with { "grace_period_hours": 24 } — mints a new whsec_... secret and signs every delivery with both secrets in space-separated webhook-signature: v1,<new> v1,<old> during the grace window (already supported natively by standardwebhooks and client.webhooks.unwrap()).
  • CLI parity: Add linq webhooks deliveries <SUB_ID> --failed and linq webhooks replay <DELIVERY_ID> so developers can debug and replay without leaving the terminal.

3. Reference Agent Pattern (Quickstart Update)

Ship this 20-line pattern directly in the Node & Python quickstarts so developers never hit the 10-second timeout / double-text failure mode: 

// 1. Verify raw body via Standard Webhooks + ack 200 immediately (<200ms)
// 2. Dedupe on event.event_id, enqueue async LLM run
// 3. Pass message.idempotency_key derived from event.event_id when replying
app.post('/webhooks/linq', rawBodyMiddleware, async (req, res) => {
  const event = linq.webhooks.unwrap(req.rawBody, { headers: req.headers });
  const isNew = await db.insertEventIfAbsent(event.event_id);
  if (!isNew) return res.status(200).json({ deduped: true });

  await agentQueue.enqueue({ eventId: event.event_id, payload: event });
  return res.status(200).json({ accepted: true });
});

// Worker: safe against retries even if downstream LLM/API flakes
await linq.chats.messages.create(chatId, {
  message: {
    parts: [{ type: 'text', value: agentReply }],
    idempotency_key: `reply:${event.event_id}`,
  },
});

4. Success Metrics & Rollout

  • Primary: Median Time-to-First-Successful-Run (signup → verified inbound + outbound reply) drops under 10 minutes; dead-letter recovery rate via self-serve replay >80%.
  • Guardrails: Zero breaking changes for existing 2025-01-01 and 2026-02-03 subscribers; p99 webhook dispatch latency unchanged during dual-secret signing.
